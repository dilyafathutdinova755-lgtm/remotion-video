# Плейбук: генерация роликов «ЕГЭ тренажёр»

Полная инструкция по этому проекту — архитектура, пайплайн, правила, команды.
Цель документа: любая сессия Claude Code (или другого агента с доступом к
терминалу и к этому репозиторию), впервые открывшая проект, должна суметь
по нему собрать ролики, неотличимые от уже сделанных, без переоткрытия всех
решений заново.

## 0. Кому и как это адресовать

Это инструкция для **агента с доступом к коду**: терминал, файловая система,
этот репозиторий, Remotion, Node. Обычный чат без инструментов (в том числе
claude.ai в режиме простого диалога) видео не соберёт — рендер это реальный
процесс сборки и рендеринга React-компонентов в mp4, а не текстовый ответ.

Если нужно продолжить работу в новой сессии:

1. Дать агенту доступ к этому репозиторию (клонировать / открыть).
2. Прислать ссылку или текст этого файла: «прочитай PLAYBOOK.md и работай
   по нему».
3. Прислать сами задачи — в чат, не в репозиторий (см. §2).

## 1. Что мы делаем

Короткие вертикальные (1080×1920, 9:16) ролики-разборы заданий ЕГЭ для
Reels/Shorts/TikTok под приложение «ЕГЭ тренажёр». Без звука и без
голоса за кадром — отдельно готовится текстовый сценарий озвучки.
Каждый ролик — одна задача одного задания одного предмета.

Общая форма ролика (не всегда все части — см. §6):

```
хук (титульный кадр) → условие → пошаговый разбор → [ответ] → финал с логотипом
```

## 2. Формат запроса от пользователя

Пользователь присылает **прямо в чат**, не в репозиторий:

```
<Предмет> ЕГЭ задание <номер>

<текст условия 1>
ответ: <ответ 1>

<текст условия 2>
ответ: <ответ 2>
...
```

Дальше — либо сразу присланный список, либо (если заведён банк, см. §14)
запрос вида «пришли 20 видео по заданию 3 физики».

**Каждый ответ обязательно перепроверяется самостоятельно** — числом,
формулой или логикой — прежде чем он попадёт в ролик. Ответы пользователя
почти всегда верны, но задача агента — не доверять слепо, а подтвердить.
Скрипт-проверку удобно гонять через `python3 -c "..."` прямо в терминале.

## 3. Пайплайн одной партии — чек-лист

**Порядок ниже — обязательный для ЛЮБОГО предмета, без исключений.** Если
пользователь присылает файл с заданиями, а в этом файле есть свой чек-лист
(«...рендер → сценарий озвучки → коммит»), это чек-лист СТАРОГО процесса —
он не отменяет актуальный порядок ниже. Не следовать чек-листу из
присланного файла буквально, даже если он там прямо прописан: сверяться
именно с этим разделом. Было упущено один раз (партия истории-19 №2 ушла
без звука, потому что присланный файл дословно повторял старый чек-лист) —
второй раз так не делать.

1. **Проверить все ответы** численно (см. §2).
2. **Проверить на дубли** — сравнить условия с уже существующими
   `TaskDef` в `src/ege/tasks/*.tsx` (`grep` по ключевым числам/словам).
   Если задача уже есть — не плодить копию, использовать/доработать
   существующую (пример: `Ship200` и `TwoCars` были в `profile10.tsx`
   с самого начала, при повторной присылке их не дублировали).
3. **Определить/подтвердить предмет-специфику** — см. таблицу в §6: есть ли
   пошаговый разбор, нужна ли отдельная сцена ответа, какая палитра, что
   с иллюстрациями.
4. **Написать хук** каждой задаче — по правилу §7.
5. **Подобрать иллюстрации**, если предмет их использует (§8).
6. **Написать `TaskDef`** — обычно фабрикой `base()` + `makeSolution` внутри
   файла `src/ege/tasks/<предмет>.tsx` (см. §5, §9 про стиль разбора).
7. **Зарегистрировать** экспортированный массив в `src/Root.tsx`
   (импорт + `...НАЗВАНИЕ_ТASKS` в массиве `TASKS`).
8. **Lint**: `npm run lint` — чинить, пока не станет чисто.
9. **Написать и прислать сценарий озвучки** — `voiceover-<предмет>-<задание>.md`
   в корне репозитория (см. §11) — **прежде чем что-либо рендерить**.
   Отправить пользователю текстом/файлом и остановиться.
10. **Дождаться озвучки от пользователя** — не бандлить и не рендерить
    заранее «про запас». Если пользователю сейчас неудобно слать отдельные
    файлы на каждую сцену — подойдёт один файл на задачу целиком либо
    несколько файлов с тайм-кодами, см. §11 про разметку по паузам.
11. **Разметить озвучку по секундам** (`ffmpeg silencedetect`, см. §11) и
    подставить `audioSync` в `TaskDef`, сложить mp3 в `public/audio/`.
12. **Bundle**: `npx remotion bundle src/index.ts --out-dir=build`.
13. **QA стилл-кадрами** — до полного рендера снять несколько кадров
    (`npx remotion still build <Id> out.png --frame=<N> --browser-executable=...`,
    см. §12) и посмотреть на них: не обрезаны ли иллюстрации, не наезжает ли
    текст на плашку, не разъезжается ли карточка формулы, не опережает ли
    картинка озвучку. Дешевле поймать здесь, чем после минуты рендера
    десяти роликов.
14. **Полный рендер**: `scripts/render.sh Id1 Id2 Id3 ...` (см. §12) —
    печатает длительность каждого файла, чтобы сверить с ожидаемой (должна
    совпасть с длительностью аудио).
15. **Ускорить 1.2×**, если пользователь не сказал иначе (см. §11 про
    `-itsscale`/`atempo`/`-r 72`).
16. **Коммит** с сообщением на русском, объясняющим *почему*, а не только
    *что* (см. примеры в `git log` этого репозитория) — с подписью Co-Authored-By
    и Claude-Session, как требует системный промпт сессии.
17. **Отправить пользователю** — видео через `SendUserFile` пачками
    (по 5–6 штук либо zip-архивами до 30 МБ, см. §11), плюс сценарий.

Единственное исключение — когда пользователь сам явно просит сначала
получить только сценарий или только видео-черновик без звука; тогда так и
делать, но не молчать о том, что порядок отличается от обычного.

## 5. `TaskDef` — модель задачи

Определение в `src/ege/tasks/types.ts`. Общая часть (`TaskCommon`) плюс один
из двух видов ответа.

**Общие поля:**

- `id` — id композиции Remotion, используется в имени файла. **Только
  латиница/цифры/дефис** — Remotion не принимает `_` и другие символы в id
  композиции (было падение рендера на `Oge8_01`, переименовано в
  `Oge8Chetyresta`).
- `number` — номер задания.
- `examType?: "ege" | "oge"` — какой экзамен: ЕГЭ (11 класс, по умолчанию)
  или ОГЭ (9 класс) — разные бренды приложения. Переключает логотип
  (`AppLogo.tsx`, текст «ЕГЭ»/«ОГЭ» вместо картинки — логотип рисуется
  вектором, отдельного файла иконки не требуется) и первую часть плашки
  хука («ЕГЭ · …» / «ОГЭ · …», `HookScene.tsx`). Всё остальное — палитра,
  тайминг, шрифты, безопасные зоны — общее для обоих экзаменов.
- `subject?` — строка вида `"в ЕГЭ по физике"`; используется для подписи
  и как fallback для выбора палитры, если `palette` не задан явно.
- `palette?: "blue" | "green" | "pink" | ...` — явный выбор палитры
  (см. §6). Без него палитра решается по `subject` в `HookScene`.
- `hook?: string | string[]` — титульный вопрос. **Всегда задавайте массивом
  строк**, если хук на кадре — это два предложения: перенос строки должен
  стоять там, где задумано, а не там, где кончилась ширина кадра
  (см. `CONVENTIONS.md` / было баг: «В яйцеклетке 8. А» отрывалось от
  «в теле?»).
- `pillLabel?` — надпись на плашке над условием («ЗАДАЧА», «ЗАДАНИЕ»…).
- `instruction?` — формулировка задания над самим условием (нужна там, где
  условие и формулировка задания — разные вещи: русский язык, история).
- `tokens: Token[]` — условие, разбитое на слова функцией `w("текст")` из
  `dsl.ts`. Даже если условие не читается вслух текстом (задание 7 по
  русскому, где вместо этого список `options`), `tokens` всё равно нужен —
  на нём базируется `TaskDef`, и `w(INSTRUCTION)` подставляется формально.
- `options?: string[]` — вместо сплошного условия: список вариантов,
  которые не читаются вслух, а появляются на экране по одному (см.
  `formword.tsx`). Выделенное слово в каждой строке пишите КАПСОМ — компонент
  `OptionList` сам находит и подсвечивает капс-слова регуляркой.
- `problemSize: number` — кегль условия; длинные тексты — мельче (обычно
  40–46).
- `illustration?: string | string[]` — картинка(и) под условием, имя файла
  из `public/illustrations` без расширения (§8).
- `solutions: SolutionScene[]` — пошаговый разбор (`{ seconds, Component }`),
  собирается `makeSolution()` из `Solution.tsx`. Пустой массив `[]` — разбора
  нет вовсе (задания 6/7 по русскому, история-19).
- `answerSeconds?` — длительность финальной сцены, когда она есть.
- `answerRecap?: boolean` — **если `false`, отдельной сцены ответа нет
  вообще** (см. §6). Это переходное поле: старые предметы (базовая
  математика, информатика, биология) его пока не используют — их ответ
  всё ещё отдельной сценой, с пояснением в `check`.

**`ValueAnswer`** (ответ — число/слово): `answerLead`, `answerFormula?`
(необязательно — не заполняйте для заданий, где считать нечего, например
русский-7: там вместо формулы — `wrongNote`), `answer`, `unit?`, `answerSize?`,
`check?`, `wrongNote?` (зачёркнутый неверный вариант из условия — только
зачёркивание, без подписи «так — неверно», см. историю правок).

**`ConceptAnswer`** (ответ — два абзаца, не число): `concept: { definition,
fact }`. Единственный сейчас потребитель — история, задание 19. Рисует
`ConceptScene`, а не `AnswerScene`.

У `ConceptAnswer`-задач нет ни пошагового разбора, ни отдельного таймера на
подумать (таймера-виджета с обратным отсчётом в проекте нет вообще ни у
одного предмета — «время подумать» всегда просто пауза в тайминге сцены,
без визуального элемента). Вместо этого `ProblemScene.tsx` рисует под
карточкой условия текст «СТАВЬ НА ПАУЗУ» капсом (`textTransform: uppercase`,
не менять текст на буквальные заглавные — так его нельзя будет одинаково
стилизовать в других местах), только когда `task.concept` задан. Пробовали
эмодзи ⏸ рядом с текстом — не отрисовалась в headless-браузере (пустой
прямоугольник, глифа нет), от иконки отказались, оставили чистый текст.

Границы условие→понятие→факт у этих задач обязаны идти строго по секундам
реальной озвучки (`audioSync.answerSec` / `audioSync.factAtSec`), не на
глаз — см. §11a, там же разобрана найденная на практике ошибка.

**«Разбор → отдельный ответ? Нет» = `answerRecap: false`.** Правило:
если у задачи есть пошаговый разбор, последний шаг и есть ответ — повторять
его следующим кадром бессмысленно. Именно так сейчас устроены математика-10 и
физика-3: последний шаг `solutions` заканчивается акцентной карточкой-ответом
и строкой пояснения (хелпер `finish()` в конце файла задачи), а сцены
`AnswerScene` для них вообще нет — `buildScenes()` в `timing.ts` даёт
`answer: 0`, и `EgeVideo.tsx` её пропускает.

**Долг:** базовая математика, информатика и биология ещё не переведены на
`answerRecap: false` — их пояснение живёт в поле `check` на сцене ответа.
Если переводить — пояснение нужно перенести в последний шаг `solutions`
(строкой `line(<span style={NOTE}>...</span>)` после финальной `card`),
иначе оно пропадёт вместе со сценой. Пример переноса — коммит, где `ship200`
и `twoCars` переехали в `profile10.tsx`.

Разбор, где он есть, должен объяснять решение человеку, который тему не
знает: перед формулой — что она значит и откуда взялась, зачем это
обозначение; корни квадратного уравнения — с явным дискриминантом, а не
внезапно появившимся числом; единицы измерения переводятся с объяснением
(«40 г = 0,04 кг — в физике всё считаем в килограммах»); там, где решение
можно сократить рассуждением вместо формул (сплавы 15%/25%/20% → середина →
поровну), явно проговорить это рассуждение, а не решать системой уравнений
для вида.

## 7. Правило хука: никогда не выдавать ответ

Хук — это общий вопрос-завлекалка, а не подсказка. Формулировки вроде
«Решишь за 10 секунд?», «Спорим, не решишь?», «Здесь есть подвох» подходят
к любой задаче. Формулировка вроде «Пирог с чем?» в задании со списком
вариантов **называет тот самый вариант, где ошибка**, и решает задачу
раньше, чем зритель увидел список — это подтверждённая, отснятая ошибка
восьми хуков из десяти в `formword.tsx` (Rus7Povidlo1/2, Rus7Okrep,
Rus7Krasivee, Rus7Mesyatsy, Rus7Mongolov, Rus7Chetyrem, Rus7Ih — переснять,
когда дойдут руки).

Правило касается **любого задания с выбором из нескольких вариантов**
(в первую очередь русский язык, задания 6 и 7). В задачах на счёт хук
может опираться на числа из условия («Мяч летит вверх. Как высоко?») — там
это не подсказка, это интрига.

По той же причине **для заданий со списком вариантов (`options`) не
ставится иллюстрация**: любая предметная картинка так же укажет на нужный
вариант, как хук.

## 8. Иллюстрации под условием

Поле `illustration` в `TaskDef` — имя файла (без расширения) из
`public/illustrations/`, либо массив имён, если по ходу условия появляются
разные предметы (двигатель → спуск → шоссе). Список делит сцену поровну и
перетекает одна картинка в другую (логика — в `ProblemScene.tsx`,
`icons`/`slotOpacity`). Если подходит одна картинка — используйте одну, не
плодите список искусственно.

**Откуда берутся картинки.** Пользователь присылает лист-коллаж в
репозиторий (не в чат — это единственное исключение из правила §2, потому
что файл идёт в код, а не в контент), агент режет его на отдельные PNG с
прозрачным фоном. Уже разобранные листы:

- `IMG_3805.png` — математика, сетка 5×5, без подписей.
- `IMG_3808.png` — физика, 6 колонок, под каждой плиткой подпись, которую
  надо отрезать вместе с фоном.

**Как резать новый лист** (шаблон, отработанный на обоих листах выше):

1. Скачать лист: `git show origin/main:ИМЯ.png > файл.png` после
   `git fetch origin`.
2. **Не резать ровной сеткой** — плитки на присланных листах стоят
   неравномерно, и деление `ширина / число_колонок` срезает края (у
   велосипеда пропадало колесо, у машины — бампер). Сначала найти реальные
   границы: просканировать строку/столбец пикселей и найти светлые
   (`r,g,b > ~250`) зазоры между плитками — короткий Python-скрипт с PIL,
   пример подхода — в истории коммитов (`git log --oneline | grep -i
   стикер`, посмотреть diff).
3. Вырезать каждую плитку по найденным границам, залить фон прозрачным
   (`is_bg()` + заливка от краёв через BFS/`collections.deque`, а не по
   всему изображению — иначе просядут светлые детали рисунка типа снега на
   горе).
4. Отбросить мелкие оторванные куски соседних плиток (несвязные компоненты
   меньше ~2–6% от самой большой — тоже BFS по непрозрачным пикселям).
5. Обрезать по фактическому content bbox, сохранить в
   `public/illustrations/<name>.png`, ограничив макс. сторону ~480px.
6. **Обязательно собрать контрольный лист** (contact sheet) на цветном фоне
   и посмотреть на него глазами — только так ловятся обрезанные края и
   пропавшие детали (было минимум дважды: сначала пропала пунктирная
   стрелка A→B, потом обрезались велосипед и машина).

Картинка должна иллюстрировать тему, но не выдавать ответ — тот же принцип,
что и с хуком.

## 9. Тайминг и 60 fps

`VIDEO.fps = 60` в `theme.ts`. Все длительности анимаций **исторически
записаны в кадрах при 30 fps** (спринги, задержки Reveal, шаг между
элементами в `Solution.tsx`) — при смене частоты они не должны оставаться
как есть, иначе всё ускорится вдвое, включая скорость чтения условия
(`wordFrames`), от которой зависит длина сцены с условием.

Функция `f30(frames)` в `timing.ts` пересчитывает такое число под текущий
`VIDEO.fps`. **Любая новая покадровая константа задаётся в кадрах при
30 fps и пропускается через `f30()`.** Осторожно с двойным пересчётом:
`makeSolution()` считает шаг между пунктами в кадрах-при-30fps и передаёт
его в `Reveal`, который сам вызывает `f30()` — если завернуть в `f30()`
дважды, тайминг разъедется (это был реальный баг при первом переключении на
60 fps, исправлен).

## 10. Палитра и вёрстка страницы ответа

`theme.ts` экспортирует `paletteFor(name?: PaletteName)` — палитра либо
явно указана в `TaskDef.palette`, либо (для старых предметов) угадывается
по `subject` в `HookScene`. Добавление новой палитры — скопировать блок
`BLUE`/`GREEN`/`PINK`, поменять шесть-семь опорных цветов, зарегистрировать
в `PALETTES`. Иконка приложения (`AppLogo`, через `LOGO` в `theme.ts`) —
**всегда синяя**, это бренд, её нельзя красить под палитру предмета.

Финальные сцены (`AnswerScene`, `ConceptScene`) стоят без рамок и
прямоугольников прямо на фоне: ответ вверху, разбор ниже, разделены тонким
волоском (`accentLine`), на фоне — декоративные `FlowLines` (бледные дуги,
не мешают чтению). Контент прижат к `SAFE_BELOW_BADGE` (400px), а не просто
к `SAFE.top` (260px) — иначе подпись над ответом уезжает под собственную
плашку «ЕГЭ тренажёр», которая висит на `top: 232`.

## 11. Сценарий озвучки

Файл `voiceover-<предмет>-<задание>.md` в корне репозитория, один файл на
партию задач. Формат:

- Заголовок партии, короткое описание тайминга/структуры.
- На каждую задачу — заголовок `## NN — короткое название`, дальше литой
  текст без режиссёрских пометок, абзацы совпадают со сменой кадров: хук →
  условие → шаг(и) разбора → ответ/пояснение → финал («Скачивай бесплатно.
  Ссылка в шапке профиля.»).
- Числа — словами, как проще прочитать вслух («сто пятьдесят шесть», не
  «156»).
- Фраза «Решаем задание из приложения «ЕГЭ тренажёр»» **остаётся в
  сценарии, но не выводится на экране** — так было решено с самого начала
  проекта.
- Если в кадре что-то явно неверное зачёркнуто (`wrongNote`), в сценарии
  это обязательно проговаривается словами: «Неверно сказано «...». Правильно
  — ...».
- Текст сценария должен **дословно соответствовать тому, что показано на
  экране** после последней правки разбора — при любой правке текста в коде
  сверяйте сценарий и обновляйте его тем же коммитом.

## 11a. Реальная озвучка: разметка, вставка в видео, ускорение

Отработано на профильной математике (партия 2, 20 роликов) — см. `git log`
за конец августа 2026. Пользователь пишет озвучку сама (ElevenLabs) по
присланному сценарию (§11) и присылает mp3.

**Формат файлов от пользователя.** Лучше всего — один файл на одну задачу
целиком (не на весь ролик по кусочкам, не общий файл на несколько задач):
тогда границы между задачами не нужно угадывать, а разбор одной короткой
задачи (30–50 сек) внутри самого файла достаточно короткий, чтобы ошибку
там было легко перепроверить. Если пользователь присылает несколько задач
одним файлом или несколько файлов без явной привязки — обязательно
уточнить порядок явно (в этом проекте так уже путались дважды: сначала
из-за порядка прикрепления файлов в сообщении против времени их создания,
потом из-за нумерации партии). Просить называть файлы номером задачи —
самый надёжный вариант.

**У этого окружения нет распознавания речи** (ни онлайн, ни офлайн-модель),
поэтому сопоставить аудио с текстом можно только по паузам:

```bash
FF=node_modules/@remotion/compositor-linux-x64-gnu/ffmpeg
$FF -i task.mp3 -af silencedetect=noise=-30dB:d=0.35 -f null - 2>silence.log
```

Порог `-30dB` подходит для большинства записей ElevenLabs; если пауз нашлось
подозрительно мало (напр. в самом хвосте файла один гигантский «кусок
речи» длиной в половину ролика) — запись, вероятно, тише обычного, пробовать
`-25dB` / `-22dB` / `-20dB`, пока не найдутся все естественные паузы между
предложениями (было на голосе с суффиксом `Alex_Nekrasov...Confident_and_Clear`
— ему нужен был -20dB).

**Сопоставление найденных пауз с абзацами сценария.** Пауз внутри одной
задачи обычно больше, чем абзацев (TTS делает паузы почти на каждой точке,
не только на границах моих абзацев) — их нужно сгруппировать. Рабочий
способ: для каждого абзаца сценария посчитать число слов, взять его долю от
общего числа слов задачи, умножить на общую длительность аудио — это
ожидаемая длительность абзаца. Дальше динамическое программирование:
разбить N аудио-сегментов на M абзацев (M ≤ N) минимизируя сумму
относительных квадратичных ошибок между «сколько эта группа сегментов
реально длится» и «сколько по числу слов должна». Работает надёжно, если
считать **в пределах одной задачи** — если попытаться прогнать один такой
расчёт сразу на несколько задач без чёткой границы между ними, ошибка
может увести очень далеко (проверено: 6-словная фраза «Скачивай
бесплатно...» может «съесть» 30-секундный кусок аудио, если границы задач
неизвестны). Именно поэтому важно, чтобы задача была в отдельном файле.

**`TaskDef.audioSync`** (см. `types.ts`) — вместо оценки по словам, сцены
считаются напрямую из секунд начала: `conditionSec`, `stepSec: number[]`
(старт каждой сцены-шага), `outroSec`, `totalSec`. `buildScenes()` в
`timing.ts` использует их напрямую, когда поле задано; иначе — старое
поведение по словам (обратная совместимость, менять ничего в остальных
предметах не нужно).

**Шаги, где в озвучке — две-три реплики подряд** (например, «решаем» и
«ответ» — отдельные абзацы сценария, но одна и та же сцена/шаг в коде):
поле `stepBeats: Record<номер_шага, {itemCounts, atSec}>` — `itemCounts`
делит массив `SolutionItem[]` этого шага на группы (по порядку), `atSec` —
секунды начала второй/третьей группы относительно начала шага. Собирает
итоговые кадры появления `beatsToItemAt()` в `Solution.tsx`, передаётся в
`step(..., itemAt)`. **Безопасное правило деления на группы**: резать
строго по границе `finish()` (последние 2 пункта — card+line ответа), а
если перед `finish()` есть «висячая» стрелка `arrow()` — она уходит в ту
же группу, что и `finish()` (стрелка всегда должна получать время того
пункта, к которому ведёт). Не пытаться распихать пункты ответа `finish()`
*раньше*, ближе к началу шага, даже если сам ответ по смыслу
проговаривается словами уже в предыдущей реплике сценария — «раньше
сказано, чем показано» не запрещено правилом §7, а вот «раньше показано,
чем сказано» запрещено, и попытка сдвинуть карточку ответа пораньше рискует
как раз последним.

**Встраивание аудио.** Один `<Audio src={staticFile(task.audioSync.src)} />`
в `EgeVideo.tsx`, играет от кадра 0 (не оборачивать в `Sequence` со
сдвигом) — сцены уже нарезаны `buildScenes()` под секунды из `audioSync`,
поэтому обёртка не нужна. Файлы озвучки — в `public/audio/<предмет>-<N>.mp3`
(не коммитятся, см. `.gitignore`).

**Ускорение 1.2× (или как попросит пользователь).** Родной ffmpeg,
собранный вместе с Remotion (`node_modules/@remotion/compositor-linux-x64-gnu/ffmpeg`),
собран с `--disable-filters` и включает только часть фильтров — видео-фильтра
`setpts` **в нём нет** (только `asetpts` для аудио), поэтому классический
`setpts=PTS/1.2` для видео не сработает. Рабочий способ — сжать метки
времени на входе через `-itsscale`, а выходной fps поднять пропорционально,
чтобы ни один кадр не потерялся:

```bash
FF=node_modules/@remotion/compositor-linux-x64-gnu/ffmpeg
"$FF" -itsscale 0.833333 -i in.mp4 -i in.mp4 \
  -map 0:v -map 1:a -af atempo=1.2 \
  -r 72 -vsync cfr \
  -c:v libx264 -crf 18 -preset medium -c:a aac -b:a 192k \
  -shortest out.mp4
```

(`0.833333` = `1/1.2`; `-r 72` = `60*1.2` — без явного `-r` на новый эффективный
fps ffmpeg по умолчанию подгоняет кадры под старые 60fps и **роняет** каждый
шестой кадр, проверено на практике.) Второй `-i in.mp4` нужен, чтобы
`-itsscale` применился только к видеопотоку, а не исказил обработку звука,
который и так растягивается через `atempo`.

**Лимит на вложение — 30 МБ** (жёсткий, у `SendUserFile`). Партия из
15–30 роликов обычно не помещается одним файлом — резать на zip-архивы по
5–6 роликов (`zip -0` — без пересжатия, видео и так уже сжато) и слать по
2–3 архива за вызов `SendUserFile`.

**Границы сцен у `ConceptAnswer` (история-19) — где именно резать.**
Была найдена и подтверждена пользователем ошибка (2026-08-31, на партии из
20 понятий): если тайминг не привязан к реальным секундам начала фраз в
озвучке, то а) переход со сцены условия на сцену понятия может произойти
раньше, чем в озвучке заканчивается фраза «Факт не должен повторять
определение» — конец этой фразы «утекает» на уже открывшийся следующий
слайд; б) внутри сцены понятия блок «Факт» может появиться до того, как
диктор закончил произносить «Смысл понятия». Оба случая — нарушение
базового правила синхрона (визуал не должен опережать озвучку).

Правильная разбивка (реализовано в `AudioSync.answerSec` / `AudioSync.factAtSec`,
`timing.ts` → `buildScenes()`, `ConceptScene.tsx`):

- **условие → понятие**: ровно там, где в озвучке начинается фраза
  «Смысл понятия» — это и есть `answerSec`. Всё, что происходит раньше
  (включая хвост «...Факт не должен повторять определение.»), обязано
  оставаться на сцене условия целиком.
- **понятие → факт** (внутри одной сцены `ConceptScene`): ровно там, где
  начинается слово «Факт» — это `factAtSec`, из которого высчитывается
  относительный кадр `Reveal at` (`(factAtSec - answerSec) * 30`).

Оба значения находятся тем же DP-выравниванием по паузам, что и остальной
тайминг (§ выше) — как **отдельные границы между абзацами сценария**, а не
подбираются на глаз. Без `audioSync` (черновой/silent-режим, старый
`answerSeconds` + захардкоженный `Reveal at={52}`) правильность этих границ
никак не гарантирована — такой режим годится только для черновой проверки
вёрстки по стилл-кадрам, но **не для финального ролика**: концепт-задачи
(`task.concept`) нельзя отдавать пользователю без реального `audioSync`.

## 11b. Рендер по одной задаче из n8n (GitHub Actions)

Отдельный путь для одиночных динамических роликов, минуя ручную партийную
процедуру из §2–§3: n8n готовит текст и озвучку для одной задачи и сама
дёргает `POST /repos/{owner}/{repo}/actions/workflows/render-on-demand.yml/dispatches`
с тремя полями — `task_id`, `task_data` (JSON: `exam, subject, task_number,
condition_text, answer, voiceover_text, account`), `audio_url` (ссылка на
mp3 в Google Drive). Файл: `.github/workflows/render-on-demand.yml`.

Что делает воркфлоу по шагам:

1. Скачивает mp3 по `audio_url` через `gdown --fuzzy` (сам разбирается с
   форматами ссылок Drive и с interstitial-подтверждением для больших
   файлов).
2. `scripts/dynamic-task/align.py` — по тексту `voiceover_text` и аудио
   восстанавливает `AudioSync` (тот же DP-метод выравнивания пауз, что и в
   ручной разметке, см. §11a), **без ручной проверки**.

   **Фиксированный порядок сегментов** (подтверждено на реальном коде n8n,
   не меняется):
   1. вступление («Решаем задание 6 по русскому языку из приложения
      „ЕГЭ Тренажёр“»);
   2. `condition_text` — дословно то же самое, что показано на экране;
   3. explanation — объяснение решения;
   4. «Ответ: …» (с любым тире/двоеточием после);
   5. CTA («Скачивай бесплатно...»).

   Важно: explanation звучит **до** «Ответ:», а не после. Под ответом на
   экране (`AnswerScene`) объяснение всё равно показывается — просто озвучено
   оно было раньше, ещё при показе карточки условия; сама сцена ответа не
   меняется (ответ и объяснение появляются вместе, без отдельной паузы на
   озвучку объяснения внутри этой сцены — она уже прозвучала).

   Кроме «Ответ:» и CTA-маркера скрипту нужен третий ориентир — конец
   `condition_text`, иначе не отличить условие от объяснения внутри одного
   и того же блока перед «Ответ:». Поэтому `align.py` принимает
   `--condition-text` (то же самое значение, что и в `task_data.condition_text`)
   и ищет его подстрокой в номализованном тексте, накапливая предложения по
   одному — так `condition_text` может занимать и несколько предложений.
   Если текст не соответствует шаблону (нет «Ответ:», нет CTA, не нашёлся
   `condition_text`, или он обнаружился ПОСЛЕ «Ответ:» — порядок нарушен) —
   скрипт падает с понятной ошибкой, а не угадывает: лучше видимый сбой CI,
   чем тихо разъехавшийся по времени ролик.

   **Числа в `voiceover_text` для TTS — production-grade нормализатор.**
   ElevenLabs должен получать текст, где числа/формулы записаны так, как их
   реально произносят («шесть», не «6»; «две тысячи восьмом» для года «2008»
   в контексте «в 2008 году»; «аш-два-о» для «H2O»). `task_data` на видео
   (`condition_text`, `instruction`, `explanation`, `answer`, `task_number`,
   сам `voiceover_text`) при этом остаётся буквально исходным — нормализация
   применяется только к отдельной копии.

   Единый источник — `scripts/dynamic-task/normalize-for-voiceover.mjs`,
   главная функция `normalizeForVoiceover(text, subject)`. Конвейер:
   общая нормализация (даты/годы/десятилетия/века — с падежным
   согласованием; порядковые через дефис «6-й/6-го/6-му»; десятичные дроби;
   проценты; дроби и отношения «2:3»/«1:100000»; IP-адреса; системы
   счисления; химические формулы, разбираемые алгоритмически по таблице
   символов элементов, а не списком; единицы измерения — физика, география,
   информатика; математические степени/корни/функции/интервалы; греческие и
   латинские буквы; инициалы «А. С. Пушкин»; аббревиатуры по словарю с
   заранее заданными исключениями типа «ЕГЭ»→«егэ», остальные — по буквам
   через `CYRILLIC_LETTER_NAMES`) → предметные надстройки для химии/биологии/
   информатики (`normalizeChemistry`/`normalizeBiology`/
   `normalizeInformaticsSubject`, у остальных предметов — тот же общий
   конвейер) → `safeFallbackForUnknownToken` (последняя страховка: то, что
   не разобралось ни одним правилом, но похоже на цифры/операторы/греческие
   буквы, разбирается по символам, а не улетает в TTS сырым). Предмет
   определяется по `task_data.subject` через `subjectKeyFromText` (десять
   предметов ЕГЭ + `unknown`-фолбэк на общий конвейер). `findUnsafeTtsTokens`
   — диагностика поверх уже нормализованного текста, не мутирует его.

   Тесты (154, с запасом над требуемым минимумом 150):
   `node scripts/dynamic-task/test-normalize-for-voiceover.mjs`.

   **Одна логика для n8n и GitHub** (не две ручные копии, которые разойдутся):
   канонический источник — `normalize-for-voiceover.mjs`; генератор
   `scripts/dynamic-task/build-n8n-voiceover-normalizer.mjs` собирает из него
   self-contained JS без единого `import`, готовый целиком вставляться в
   n8n Code node — `generated/n8n-normalize-for-elevenlabs.js`. Файл
   закоммичен (не только сгенерирован налету) — коллеге не нужно уметь
   запускать Node, чтобы обновить n8n-ноду. Пересобрать после правок
   исходника: `node scripts/dynamic-task/build-n8n-voiceover-normalizer.mjs`.
   n8n Code node, который нужно ЗАМЕНИТЬ этим файлом целиком — тот, что
   готовит текст непосредственно перед узлом ElevenLabs (нода
   вызова ElevenLabs остаётся как есть, меняется только код,
   формирующий её текстовый вход). Сгенерированный файл на выходе
   добавляет к каждому item три поля, не трогая остальные:
   `voiceover_tts_text` (произносимый текст для ElevenLabs),
   `tts_normalization_warnings` (пусто на известных конструкциях),
   `tts_normalizer_version` ("2.0").

   **align.py использует ИМЕННО тот текст, что ушёл в ElevenLabs, а не
   пересчитывает заново.** `print-normalized-voiceover.mjs`: если в
   `task_data` уже есть `voiceover_tts_text` (n8n прислал — тот самый текст,
   что реально попал в TTS) — используется он один в один, без повторной
   нормализации (другая версия правил могла бы дать не побайтово ту же
   строку). Если поля нет (ручной тест / n8n ещё не обновлён) — считается
   на месте по `voiceover_text` + `subject`, с предупреждением в stderr.
   В `render-on-demand.yml` `--text` для `align.py` берётся из
   `print-normalized-voiceover.mjs` (тайминг), `--display-text` и
   `--condition-text` — из исходного `task_data` с цифрами (что показать на
   экране в `checkLines`/для сверки границы условия).
3. `scripts/dynamic-task/build-dynamic-task.mjs` — собирает из `task_data` +
   результата `align.py` один `TaskDef` и пишет его в
   `src/ege/tasks/_dynamic.generated.tsx` (в репозитории этот файл всегда
   пустой стаб — CI переписывает его транзитно и никогда не коммитит
   обратно). Правила внутри:
   - `examType` — по подстроке «огэ»/«oge» в `task_data.exam`.
   - Палитра — по правилу §10: «биолог» → зелёная, «русск»/«истор» → розовая,
     иначе синяя (проверяется подстрокой в `task_data.subject`).
   - Пошагового разбора нет никогда (`solutions: []`) — у `task_data` нет
     поля для шагов, это поток для простых прямых ответов.
   - Хук — не из содержания задачи (в `task_data` нет отдельного поля под
     него, а придумывать по условию рискованно: можно случайно выдать
     ответ), а один из небольшого фиксированного набора безопасных общих
     вопросов, выбранный детерминированно по `task_id`.
   - Пояснение под ответом (`check`) в динамическом рендере **сознательно не
     заполняется вовсе** — `AnswerScene` показывает только сам ответ. Оно и
     так уже прозвучало (сегмент explanation звучит ДО «Ответ:», пока на
     экране ещё карточка условия — см. фиксированный порядок сегментов
     выше), повторять его текстом под ответом не нужно. `align.py`
     по-прежнему кладёт explanation в `checkLines` (полезно для отладки),
     но `build-dynamic-task.mjs` эти строки просто не использует. Ручные
     задания (rus6/7, химия-11 и т. д.) сами заполняют `check` в своих
     файлах — их это не касается, `AnswerScene.tsx` не менялся.
   - Формулировка задания (`instruction`) — приглушённый, полупрозрачный блок
     ВНЕ основной карточки (свой `<div>` перед `<ProblemCard>` в
     `ProblemScene.tsx`, не внутри неё — раньше он по ошибке был внутри
     карточки у всех предметов с `instruction`, не только у динамических
     задач; исправлено для всех разом). Карточка ниже несёт только само
     условие (`tokens`/`options`). У заданий 7 и 8 по русскому формулировка
     стандартна и не меняется от варианта к варианту (как в `formword.tsx` /
     `oge8.tsx`) — берётся из встроенной таблицы `STANDARD_INSTRUCTIONS`, а не
     из `condition_text` целиком. Если `condition_text` уже включает этот
     текст — он вырезается из `tokens`, чтобы не показать дважды. Для заданий
     без стандартной формулировки (номер не в таблице) n8n может передать её
     явно полем `task_data.instruction`.
4. `npx remotion render` — обычный рендер, без отличий от ручного пути.
5. Готовое видео уходит и артефактом GitHub Actions, и (если настроены
   секреты) на Google Drive в ту же папку, что и n8n; ссылка идёт в теле
   вебхука. Финальный шаг — `POST` на **продакшен**-вебхук n8n
   (`.../webhook/video-ready`, не `webhook-test`) с
   `{task_id, video_url, status: "готово"}`.

Секреты репозитория, которые нужны для загрузки на Drive (без них рендер и
вебхук всё равно проходят — просто `video_url` в вебхуке будет ссылкой на
артефакт GitHub Actions, а не на Drive):

- `GDRIVE_SERVICE_ACCOUNT_JSON` — весь JSON-ключ сервис-аккаунта целиком.
- `GDRIVE_FOLDER_ID` — id папки на Drive, расшаренной на email сервис-
  аккаунта с правом Editor.

Загрузка на Drive сделана без добавления `googleapis` в зависимости проекта:
`scripts/dynamic-task/gdrive-upload.mjs` подписывает JWT сервис-аккаунта
`node:crypto` и обращается к Drive API напрямую через `fetch`.

## 12. Команды-шпаргалка

```bash
# Проверка типов и стиля
npm run lint

# Пересборка бандла (после любой правки src/)
npx remotion bundle src/index.ts --out-dir=build

# Список композиций с длительностями (после bundle)
B=/opt/pw-browsers/chromium_headless_shell-1194/chrome-linux/headless_shell
npx remotion compositions src/index.ts --browser-executable=$B | grep <Префикс>

# QA-кадр без полного рендера
npx remotion still build <Id> /tmp/check.png --frame=<N> --browser-executable=$B

# Рендер партии + печать длительностей
scripts/render.sh Id1 Id2 Id3

# Проверка ответа руками
python3 -c "print(...)"
```

Готовый Chrome лежит в `/opt/pw-browsers/chromium_headless_shell-1194/…` —
**не запускать `remotion still/render/compositions` без
`--browser-executable`**, иначе Remotion попытается скачать браузер с
`remotion.media`, а этот хост закрыт egress-прокси (см. §13).

`ffprobe`/`ffmpeg` в системе может не быть — проверка длительности рендера
через разбор атома `mvhd` в заголовке mp4 (см. `scripts/render.sh`), а не
через `ffprobe -show_entries`.

## 13. Ограничения окружения (важно, не пытаться обойти)

Egress-прокси этой сессии блокирует всё, что не в явном allowlist. Проверено
и подтверждено заблокированным: `remotion.media` (скачивание браузера),
`api.elevenlabs.io` (озвучка через API), `drive.google.com`,
`dilyafathutdinova755.app.n8n.cloud`, `fipi.ru`/`ege.fipi.ru`
(официальный банк заданий), сторонние зеркала банка (`100points.ru`),
и даже `en.wikipedia.org` — то есть открытого веб-доступа с этой сессии
фактически нет. Из этого следует:

- **Автономный парсинг банка ФИПИ невозможен** в этом окружении. Задачи
  приходят только от пользователя, текстом в чат (§2).
- **Голос через API генерировать нельзя** — только текстовые сценарии
  озвучки (§11); озвучку пользователь делает сама или в другом инструменте.
- **Рендер по одной задаче с Google Drive/n8n тоже нельзя дернуть из этой
  сессии** — это и есть причина, по которой шаг «озвучка → рендер → отдать
  в n8n» вынесен в GitHub Actions (§11b): у раннеров GitHub полный доступ в
  интернет, у этой сессии — нет.
- Если в другой сессии/окружении egress устроен иначе — эти пункты можно
  переоценить, но не предполагать по умолчанию.

Git push из этой сессии периодически блокировался (403) — доступ на запись
в GitHub не был выдан сессии в моменте. Если push не проходит: продолжать
работать локально, коммитить как обычно, явно сказать пользователю, что
изменения не ушли в удалённый репозиторий и существуют только в текущем
контейнере — не изобретать обходных путей и не молчать об этом.

## 14. Банк задач и защита от повторов

Если пользователь заводит файл-банк на сотни задач (см. обсуждение — прислан
в чат, не в репозиторий) и просит партиями («пришли 20 видео по такой-то
теме»):

1. Завести `used-tasks.md` в репозитории — по одной строке на уже
   сгенерированную задачу: id композиции, предмет, номер задания, короткая
   сигнатура условия (первые слова или ключевые числа), дата.
2. При каждом новом запросе партии — сверяться с этим файлом, не выдавать
   повторов, даже если формулировка в присланном банке отличается
   косметически (тот же неверный вариант «повидлом», разные рамки условия).
3. Каждую выданную партию — дописывать в `used-tasks.md` тем же коммитом.

Файл банка от пользователя в репозиторий не кладётся (см. §2) — только
результат его использования (`used-tasks.md`) и сгенерированные `TaskDef`.

## 15. Известные открытые долги

- Базовая математика, информатика, биология — не переведены на
  `answerRecap: false` (§6).
- Русский-7: восемь хуков из десяти нарушают правило §7, ждут пересъёмки.
- ~30 коммитов в этом проекте не запушены в GitHub из-за 403 (§13) — при
  первой возможности запросить доступ на запись и разгрести.
- `render-on-demand.yml` (§11b) не прогонялся ни разу целиком на реальных
  данных — из этой сессии нельзя дойти ни до Google Drive, ни до n8n (§13).
  Проверено локально по частям: `align.py` и `build-dynamic-task.mjs`
  прогнаны на синтетическом аудио и реальном `TaskDef`-типе (`tsc --noEmit`
  проходит чисто), но сам `npx remotion render` в этой сессии не
  запускается — скачивание headless-браузера тоже заблокировано (§13).
  Первый реальный прогон должен быть либо вручную через Actions →
  Run workflow, либо первым настоящим вызовом от n8n.
